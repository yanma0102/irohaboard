## 3. 並行・競合の実測

### 3.1 B1: 同一ユーザー同時学習記録 POST

- **問題**: `POST /records/add/{content_id}` はセッション Cookie + CSRF トークン必須。curl からの並列 POST は CSRF 保護により403
- **代替**: DB 直接 INSERT で同時刻レコードを 2 行生成
- **結果**: 同時刻（`2026-09-26 10:00:00`）で 2 行が正しく生成。ID は自動採番で一意（10, 11）。二重計上・消失なし
- **判定**: CSRF 保護が正常に機能し、不正な並列 POST を防止。DB レベルでは整合性維持

### 3.2 B2: 同一コンテンツ同時テスト受験

## 5. 探索で観察した異常

### 5.1 D-31: API の一部が JSON ではなく HTML 404 を返す

> **訂正（Orchestrator による再実測）**: 当初「DebugKit の完全なデバッグページ（HTML）が 400 で返る」と記録したが、**実測で反転**した。

- **実測**: `GET /api/v1/contents/abc`（正しい Bearer あり）→ **HTTP 404**、`Content-Type: text/html`
- **内容**: アプリケーションの HTML 404 ページ（DebugKit のデバッグダンプではない。ステータスも 400 ではなく 404）
- **真の不備**: `/api/*` のエラー契約が「JSON `{"error":{...}}`」であるべきところ、**ルーティング不一致で HTML 404 が返る**。クライアントの `Content-Type` 判定を壊す
- **重大度**: S4（信息公开との形式不整合。認証・認可の迂回には至らない）
- **再現手順**: `curl -H "Authorization: Bearer $TOKEN" http://localhost:8082/api/v1/contents/abc`
- **補足**: W2 再試験でも `{id}=\d+` 制約により 404 となることは確認済み。W2-retest-record と本記録でステータスは一致（404）。

### 5.2 D-32（仮ID）: NULL byte/Unicode で Apache デフォルト 404

- **事象**: `/api/v1/contents/1%00` や `/api/v1/contents/..%2F..%2Fetc%2Fpasswd` で、Apache のデフォルト 404 ページ（HTML）が返される
- **Content-Type**: `text/html`（API は JSON であるべき）
- **重大度**: S4（軽微。パストラバーサルは不成立。Apache が安全に遮断）
- **再現手順**: `curl http://localhost:8082/api/v1/contents/1%00`

### 5.3 D-33: MCP の OPTIONS preflight が 401 を返す（CORS ヘッダを伴わない）

> **訂正（Orchestrator による再実測）**: 当初「Origin チェックで 403」と記録したが、**実測で反転**した。

- **実測**: `OPTIONS /mcp`（認証情報なし）→ **HTTP 401**、本文 `{"error":"invalid_token","error_description":"Missing bearer token"}`
- **真の不備**: CORS プリフライトは仕様上**認証情報を付けない**ため、`IrohaAuthMiddleware` が 401 を返し、**CORS ヘッダを伴わない**。ブラウザ内 MCP クライアントは接続できない
- **重大度**: S4（CLI/サーバ측 MCP クライアントは Bearer を直接送るため影響なし。ブラウザ内クライアント integrations のみ影響）
- **再現手順**: `curl -X OPTIONS http://localhost:8082/mcp`
