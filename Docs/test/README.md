## 2. 試験項目の記述形式

各ファイルは章（機能単位）ごとに次の表を持つ。**1行 = 1試験項目**。

| 項目ID | 分類 | 対象 | 前提条件 | 手順 | 期待結果 | 設計参照 | 自動化 | 優先 | 結果 | 証跡 |
|---|---|---|---|---|---|---|---|---|---|---|

- **分類**: `正常系` / `異常系` / `境界値` / `権限` / `セキュリティ` / `回帰` / `整合性` / `UI` / `性能`
- **前提条件**: 必要なロール、ログイン状態、DBデータ、設定値。データ投入が必要な場合は「§5 テストデータ」のデータセット名（`DS-1` 等）を参照する。
- **手順**: 番号付き。複数手順は `<br>` で区切る（`Docs/dev/manual-test-checklist.md` と同形式）。
- **期待結果**: 画面表示・HTTPステータス・リダイレクト先・DB変化・ログ出力を具体的に記載。文言まで指定する。
- **設計参照**: `Docs/design/*` の該当章、`Docs/API.md` の該当節、既存ID（T1-1 / A1 / R1 等）を併記。既存41ケースとの対応をここで担保する。
- **自動化**: `済`（既存PHPUnit/自動スクリプトでカバー済） / `可`（自動化可能・未実装） / `難`（目視・主観依存）
- **優先**: `P0`（移行起因の主要機能破壊に直結。必須） / `P1`（実運用で頻出。必須） / `P2`（網羅性・堅牢性向上）
- **結果**: `□`（未実施） / `OK` / `NG` / `N/A`（実施不能。理由を証跡欄に記載）
- **証跡**: NG時の再現ログ、`curl` 出力、スクリーンショット名、実行したDBクエリと結果、`logs/error.log` の該当行など。自動実行の場合は実行コマンドと結果ファイル名。

## 3. 前提データ（DS: Data Set）

画面用実データは現状空であるため、試験実施前に以下を投入する（終了後に削除し、ベースライン `ib_users`=admin 1件のみ / 他コンテンツ系0件に戻す）。

| セット | 内容 | 主な用途 |
|---|---|---|
| `DS-0` | 素の状態（admin 1件のみ） | 空一覧・404・権限の異常系 |
| `DS-1` | グループ2件（公開/非公開）、ユーザー: admin / manager / user を各1件以上、承認済み受講登録 | 権限・ログイン・ユーザー管理 |
| `DS-2` | コース2件＋コンテンツ全種（`html` / `movie` / `url` / `file` / `test` / `enquete`）、公開/非公開混在 | コンテンツ表示・DL・受験 |
| `DS-3` | テスト問題（`single` / `text`、複数正解、`score` 境界 0/100/-1）、アンケート問題 | 採点・バリデーション |
| `DS-4` | 学習記録（合格/不合格/未完了、理解度0〜5）、`ib_records.group_id` に不整合行を1件 | 履歴CSV・DB整合性 |
| `DS-5` | お知らせ3件（全体/グループ限定/非公開）、設定値一式 | お知らせ・設定 |
| `DS-6` | 旧SHA1ハッシュのユーザー1件（`sha1(legacy_salt . pass)`） | 旧パスワード互換（`AUTH-*`） |

## 4. 実施手順

1. 環境起動: `docker compose up -d` 後、`http://localhost:8082/` が 200 であることを確認。
2. `DS-0` で「空状態」項目を実施 → `DS-1`〜`DS-6` を投入。
3. 各ファイルの P0 → P1 → P2 の順で実施。ログイン系は**最後**にまとめる（ログイン画面の GET はセッションを破棄するため）。
4. 各項目の結果・証跡を表に記入。NG は事象・再現手順・`file:line` 推定原因を証跡欄に記録。
5. 全完了後、`traceability.md` の未対応欄が空であることを確認。
6. `DS-1`〜`DS-6` を削除してベースラインに復元（§3 の行数に一致することを確認）。

## 5. 判定基準

| 判定 | 条件 |
|---|---|
| 合格 | 手順を実行し、期待結果が得られた |
| 不合格 | 期待結果が得られなかった（移行起因か既存バグか環境起因かを切り分けて記録） |
| 該当なし | 環境制約等で実施不能（理由を証跡欄に記載） |

移行全体の判定は `Docs/dev/manual-test-checklist.md` §8 に準ずる。**P0 項目に1件でも不合格（移行起因）がある場合は移行失敗**とし、原因修正と再試験を必須とする。

## 6. 自動化方針

- 既存: `tests/TestCase/**`（Model/Table 中心、57テスト）。実行は `DATABASE_TEST_URL` 環境変数とテスト用DBが必要。
- 移行中に作成した回帰スクリプト（`/tmp/opencode/` 配下の `crawl.py`、`apicheck.py`、`exportcheck*.py`、`groupfiltercheck.py`、`previewcheck.py`、`routeprobe*.php` 等）はローカル検証用。恒久化するものは `tests/` へ移植する。
- したがって「自動化」列の `可` は次の優先順に自動化する: ① API 全エンドポイントの 2xx/4xx 契約テスト（PHPUnit `Controller/`）、② バリデーション境界値（既存 Table テストへ追加）、③ CSV出力のヘッダ/行数/文字コード検証、④ ルーティング全件の解決確認。

## 7. 記録の運用

- 結果は本マトリクスに直接記入し、NG は備考・証跡に必ず残す。修正後の再試験は結果を上書きし、証跡に再試験日を追記する。
- 実装と期待結果が乖離した場合は、原則として**実装側を設計書に合わせて修正**する。設計書からの意図的な逸脱は証跡に理由を明記し、設計書側を更新する。
