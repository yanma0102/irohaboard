## 0. なぜ E2E を機械的検証にとどめないか

機械的（スクリプト/チェックリスト）検証は、**あらかじめ想定した期待結果**との一致しか見られない。しかし実際の欠陥は次に潜む。

- **想定外の組合せと順序** — 途中でブラウザバック、二重送信、別タブ、セッション切れ。
- **暗黙の前提のズレ** — 設計者が「当然こう使う」と思った導線をユーザーが辿らない。
- **累積作用** — 大量データ・長期運用・権限変更後に初めて表れる不整合。
- **体験の質** — 動くが分かりにくい、遅い、不安を与える、アクセシビリティを欠く。
- **悪意ある使い方** — 仕様の隙間を使った権限逸脱・ビジネスロジック悪用。

そこで本ドキュメントは、**シナリオ（業務ジャーニー）**と**時間制の探索的セッション（チャーター）**で、人間の判断・直感・好奇心を検証の主要な道具として設計する。判定は「期待値との一致」ではなく、**複数オラクル**（設計書、旧実装、業界標準、ユーザーの期待、開発者の直感）と**重大度**で行う。

### 非機械的検証の原則

1. **時間制（タイムボックス）** — セッションは 45〜90 分。延長は成果に応じて判断。
2. **チャーター駆動** — 目的・対象・狙いを明文化。自由すぎても窮屈すぎてもいけない。
3. **テストオラクルを意識** — 「何をもって誤りとするか」を都度自覚する。
4. **記録は軽量に** — 見つけた問題・気づき・未探索を残す。網羅の証明ではなく発見の記録。
5. **探索と確認の分離** — 探索で見つけた疑いを、後で再現手順付きの検証項目として確定する。
6. **多数の視点** — ロール・言語・端末・熟練度の異なる視点で行う。

| VR-E2E-010 | 障害発生と回復 | P6 | 運用中に DB 断/ディスク満杯/アップロード中断 | 安全なエラー、データ半端なし、復旧後正常 | P1 |
| VR-E2E-011 | 大規模運用 | P4/P2 | 受講者 100 名・履歴 10 万行で一覧/検索/CSV/トップ | 実用的な速度。集計一致。UI が破綻しない | P2 |
| VR-E2E-012 | アクセシビリティ受講 | P7 | キーボードのみ＋スクリーンリーダーで受講完了 | 到達・理解・操作可能。フォーカス/ラベル/見出し妥当 | P1 |

### 2.1 シナリオの実行形式

1. **事前準備**: DS を投入し、ペルソナのロールでログイン。
2. **実施**: ステップを「ユーザーの意図」で辿る。機械的な項目チェックではなく、**その場の気づきを記録**する。
3. **逸脱の許容**: 本来の導線から外れたくなったら外れる（例: 別タブ、戻る、誤クリック）。それが探索の価値。
4. **記録**: §6 セッションシートに、発見・疑問・期待とのズレを記録。
5. **確定**: 再現する欠陥は検証項目（`02`〜`04`）に昇格し、再現手順と重大度を付す。

## 5. 使用性・アクセシビリティ・視覚品質 E2E

### 5.1 使用性（U）

- **初回完走性**: P1 がドキュメントなしで主要ジャーニーを完了できるか。
- **エラー回復性**: エラー時に「何が起きたか・どう直すか」が分かるか。
- **一貫性**: 同じ操作は同じ場所・同じ言葉・同じ見た目か（新旧画面の混在を許容範囲か）。
- **フィードバック**: 保存・送信・失敗が即座に分かるか（二重送信の不安がないか）。
- **効率**: 常連 P2 が無駄なく反復できるか（ショートカット、検索、一括）。

### 5.2 アクセシビリティ（Y）— WCAG 2.2 AA 主要基準

| 基準 | 確認内容 | チャーター |
|---|---|---|
| 1.1 代替 | 画像/Markdown 画像/アイコンに alt・代替 | CH-17 |
| 1.3 適応 | 見出し階層、ラベル、テーブル構造、フォーム関連付け | CH-17 |
| 1.4 判読 | コントラスト比 4.5:1、テキスト拡大 200% で崩れない | CH-18 |
| 2.1 キーボード | 全機能がキーボードのみで操作可能、トラップなし | CH-17 |
| 2.4 移動 | フォーカス可視、スキップリンク、ページタイトル、フォーカス順 | CH-17 |
| 3.3 入力支援 | エラー特定・説明、ラベル、必須表示 | CH-24 |
| 4.1 互換 | 名前/役割/値、ステータスメッセージの通知 | CH-17 |

### 5.3 視覚品質（U/デザイン）

- 余白・整列・一貫したコンポーネント。
- 情報階層（重要操作が目に入るか）。
- 長文・表・コード・画像の破綻がないか。
- 新旧画面のトーン統一（移行の痕跡が体験を損ねないか）。
- レスポンシブ（PC/タブレット/スマホ）と折り返し。
- `docs/ui-verification/*.png` を基準画像として視覚回帰の参照にする。

> **UI の見た目・操作感に関する指摘は、修正が必要な場合 `@designer` の領域**。検証では「どこが・なぜ問題か」を記録し、修正は設計判断として扱う。

## 6. 性能・負荷・障害 E2E

| 種別 | 内容 | 手段候補 | 合格目安 |
|---|---|---|---|
| 体感性能 | 主要画面の応答 | 手動計測 + `curl` 時間 | 2〜3 秒以内 |
| 構造性能 | N+1、重複クエリ | `logs/queries.log` / DebugKit | 件数比例の増加なし |
| 負荷 | 同時 50〜100 ユーザー | k6 / locust（要導入） | エラー率 <1%、応答劣化が許容内 |
| 容量 | 履歴 10 万行、大容量ファイル | データ生成 | タイムアウト/メモリ超過なし |
| 障害 | DB 断、ディスク満杯、中断 | 手動注入 | 安全なエラー、データ保全 |
| 復旧 | バックアップ→リストア、ロールバック | `rollback-procedure.md` | 完全復旧 |

> 負荷ツール（k6 等）は未導入。導入提案は `06` §4。

### 7.1 重大度

| 重大度 | 定義 | 対応 |
|---|---|---|
| S1 | データ破壊・権限逸脱・認証突破・情報漏洩・業務停止 | 即修正、検証項目へ昇格（P0） |
| S2 | 主要機能の不具合・誤結果 | 修正必須（P1） |
| S3 | 使用性・表示・文言の問題 | 計画的改善（P2） |
| S4 | 軽微・好み | 記録のみ |

## 8. 報告とトリアージ

1. **集約**: セッションシートを集約し、S1/S2 は検証項目（`02`〜`04`）のうち該当 ID に紐付けて確定。
2. **重複排除**: 同一根本原因をまとめる（`file:line` ベース）。
3. **昇格**: 探索で見つけた欠陥が既存項目で未カバーなら、新しい検証項目として追加する。
4. **網羅の補正**: 「未探索」が偏っていれば次回チャーターを追加（`01` §11 のセルフチェックと往復）。
5. **判断**: S1 が 1 件でもあればリリース不可。S2 は修正または明示的リスク受容。

> 本ドキュメントのチャーターは 25 種・合計目安 25〜35 時間。P0 シナリオ（VR-E2E-001〜006, 008）と攻撃者 AB-01〜AB-15 を最優先で実施する。
