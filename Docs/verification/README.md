## 0. このドキュメント群の位置づけ

本計画は、**移行完了後の現行製品**を継続的に検証するための総合計画である。

既存の `Docs/test/`（8 ファイル・**626 項目 + MCP 13 項目**）は、**CakePHP 2.10 → 5.x 移行の回帰検証**に特化して 2026-09-21 に作成された。したがって:

- 移行前後の同等性・回帰（R1〜R10）には強いが、
- 移行後に追加された **Markdown コンテンツ / Contents API Write / MCP サーバ** を十分にカバーせず、
- **探索的・濫用・使用性・アクセシビリティ・並行性・負荷**といった非機械的観点を持たない。

本計画はこれらを補完し、**現行製品のあるべき品質特性を品質特性（観点）× 対象領域 × 技法の三次元で網羅**する。既存 626 項目は破棄せず「回帰ベースライン」として再利用し、本計画から逆参照する（`01-verification-perspective-matrix.md` §6）。

> **重要な前提**: 本計画は「検証を実施する」ための設計図である。実際に全項目を実行するには相応の工数（後述 §9）とテストデータ投入が必要。まず P0 から着手することを推奨する。

## 1. 検証目的（なぜ検証するか）

1. **機能的正しさの確立** — 受講者・管理者・API 利用者・MCP クライアントに対し、仕様どおりの結果が返ること。
2. **データの正しさと一貫性** — 受講履歴・採点・進捗・権限データが失われず、集計がずれないこと。
3. **権限境界の保証** — ロール（admin / manager / editor / teacher / user）と受講登録（直接・グループ経由）の境界が破られないこと。水平・垂直の権限昇格が成立しないこと。
4. **安全性の保証** — XSS / SQLi / CSRF / パストラバーサル / ファイルアップロード / セッション / トークン / ホストヘッダの各攻撃面に脆弱性がないこと。
5. **新機能の確立** — Markdown レンダリングとサニタイズ、Contents API Write、MCP サーバ（9 ツール: 読み取り 7 + 書き込み 2 + 認証 + レート制限）が正しく・安全に動作すること。
6. **非機能品質の確認** — 使用性・アクセシビリティ・レスポンシブ・性能・並行性・回復性・運用性。
7. **回帰の防止** — 既存 626 項目を継続回帰スイートとして維持し、変更が既存機能を壊さないこと。

## 4. 検証の基本原則

1. **証拠主義** — 各項目は「手順 → 期待結果 → 実測 → 証跡」を必ず残す。NG は再現手順と `file:line` 推定原因を記録する。
2. **リスクベース** — 全項目を等価に扱わない。P0（データ破壊・権限逸脱・500・セキュリティ）を最優先する。
3. **機械的 / 非機械的の分離** — 自動検証できるものは自動化し、**人間の判断が本質**なもの（使い勝手、探索、濫用、a11y、視覚品質）は非機械的検証として明示的に設計する（`05-e2e-exploratory.md`）。
4. **再現可能性** — 前提データセット（§7）と手順のみで第三者が再現できること。
5. **破壊防止** — 検証は原則非本番。破壊的項目は本番複製環境で行い、テスト後にベースラインへ復元する。
6. **独立性** — 作成者と実行者を分けられる構造（項目は自己完結）。セキュリティ/権限の P0 は可能な限り別担当が実施。
7. **多様なテストオラクル** — 既存仕様・設計書・旧実装・業界標準（WCAG, OWASP）・直感/経験の複数オラクルで判定する。

## 6. 検証項目の記述形式

各ファイルは領域ごとの章に分かれ、**1 行 = 1 検証項目**の表を持つ。

| 列 | 内容 |
|---|---|
| ID | `VR-<領域>-###`。一意。 |
| 分類 | `正常系` / `異常系` / `境界値` / `権限` / `セキュリティ` / `整合性` / `UI` / `性能` / `並行` / `運用` / `探索` |
| 観点 | `01-...matrix.md` の品質特性コード（F/D/A/Z/V/E/S/I/U/Y/P/R/O/M） |
| 対象 | 機能・画面・エンドポイント |
| 前提 | ロール、ログイン状態、データセット（§7）、設定値 |
| 手順 | 番号付き。要点のみ（詳細は設計書参照） |
| 期待結果 | 画面・HTTP ステータス・リダイレクト・DB 変化・ログ。文言まで指定 |
| 優先 | `P0`（必須）/ `P1`（必須）/ `P2`（網羅） |
| 機械 | `済`（既存自動化あり）/ `可`（自動化可能）/ `難`（人間判断・探索） |
| 既存 | 対応する既存 ID（`FR-*` / `AD-*` / `API-*` / `AUTH-*` / `VAL-*` / `DB-*` / `NON-*` / `MCP-*`） |
| 結果/証跡 | 実施時に記入（`□` / `OK` / `NG` / `N/A` + 証跡） |

**分類と機械の対応**: `探索` および一部 `UI`/`セキュリティ`（濫用）/`並行` は `難` が基本で、`05-e2e-exploratory.md` のチャーターとして実施する。画面の網羅は `07-screen-inventory-matrix.md`、画面操作は `08-ui-operation.md`（`VR-UI`/`VR-UIS`）で担保する。

## 7. テストデータ（DS: Data Set）

既存 `Docs/test/README.md` §3 の `DS-0`〜`DS-6` をそのまま継承し、現行機能向けに拡張する。**セーダー化済み**: DS-0/DS-1/DS-2/DS-3/DS-5/DS-7 は `config/Seeds/` に実装済み（`scripts/seed-ds.sh` で一括投入可）。DS-4/DS-6/DS-8〜DS-11 は未セーダー化（手動または SQL で投入）。

| セット | 内容 | 主な用途 |
|---|---|---|
| DS-0 | 素の状態（admin 1 件のみ） | 空一覧・404・権限異常系 |
| DS-1 | グループ 2 件（公開/非公開）、admin/manager/editor/teacher/user | 権限・ログイン・ユーザー管理 |

| **DS-8（新）** | **API トークン**（有効/期限切れ/失効済/別ユーザー）と API 経由の Write 対象データ | API 認証・Write・権限 |

## 8. 優先度・判定基準

### 8.1 優先度

| 優先 | 定義 | 例 |
|---|---|---|
| **P0** | データ破壊・権限逸脱・認証突破・SQLi/XSS・主要機能の 500/全損・移行データ欠落 | 直接 URL での他人データ閲覧、API 権限昇格、採点結果の誤永続、インストール失敗 |
| **P1** | 実運用で頻出する機能不具合・UX 阻害 | ログイン/受験/CSV/アップロード/一覧表示の不具合 |
| **P2** | 網羅性・堅牢性・快適性 | 境界値の細部、レスポンシブ、i18n、性能余裕 |

### 8.2 判定

| 判定 | 条件 |
|---|---|
| 合格 | 手順実行で期待結果が得られた |
| 不合格 | 期待結果が得られない（**製品 / 既存 / 環境**を切り分けて記録） |
| 該当なし | 環境制約等で実施不能（理由を証跡に記録） |

**リリース判定**: P0 に不合格（製品起因）が 1 件でもあれば**リリース不可**。P1 不合格は修正または明示的なリスク受容が必要。

## 9. 自動化方針と工数

- **既存**: `tests/TestCase/**`（587 テスト / 2961 アサーション）。`composer test` で実行。既知 deprecation 2 件（テスト DB は `scripts/test-fresh.sh` で作り直し推奨）。表の `機械`=`済`。
- **自動化基盤（導入済）**: API 契約テスト（`ApiContractTest` 46 テスト / 339 アサーション）、Seeder DS-0/1/2/3/5/7（`config/Seeds/`、`scripts/seed-ds.sh`。DS-4/DS-6 は未セーダー化）、API スモーク（`scripts/smoke-api.sh`）、MCP スモーク（`scripts/smoke-mcp.sh`）、CI（`.github/workflows/ci.yml`：PHPUnit ブロッキング / phpcs 非ブロッキング）。
- **優先自動化**: ① API 全エンドポイントの契約テスト（Write 含む）、② バリデーション境界値、③ Markdown サニタイズ、④ MCP ツール、⑤ CSV 出力のヘッダ/行数/文字コード、⑥ ルーティング全解決。
- **自動化できないもの**: 探索的検証、濫用シナリオ、使用性/a11y、視覚品質、実負荷。`05` で人間主導の実施を設計。
- **E2E 基盤の状態**: ブラウザ自動化（Playwright 等）/axe/k6/視覚回帰は**未導入**。導入提案は `06` §3.2。
- **概算工数**: 機械的可（自動化済み分の再実行は除く）≈ 4〜6 人日、難（手動/探索）≈ 15〜25 人日、P0 集中なら ≈ 5〜8 人日（詳細 `06` §5）。

## 10. 実施サイクル

> 詳細な実行手順（環境準備・DS 投入・証跡規約・記録シート・復旧）は `09-verification-procedure.md` を参照。

1. **準備** — 環境起動 → ヘルスチェック（`/`=200）→ DS-0 で空状態項目 → DS-1〜DS-6 投入。
2. **P0 掃討** — `06` のリスク上位から P0 を全て実施。特に権限・セキュリティ・API Write・MCP。
3. **P1/P2** — 領域別に実施。ログイン/セッション系は他画面のセッションを壊すため**最後**にまとめる。
4. **非機械 E2E** — `05` のチャーターを時間制（タイムボックス）で実施し、セッションシートを記録。
5. **回帰** — 変更があれば既存 626 項目（`Docs/test/`）の該当 P0 を再実行。
6. **復元・報告** — DS を削除しベースライン一致を確認。NG は `file:line` 付きで報告。

## 12. 用語

| 用語 | 意味 |
|---|---|
| 品質特性 / 観点 | 検証で確かめる性質（機能適合性、データ整合性、…）。`01` の軸 A。 |
| 対象領域 | システムの機能/資産のまとまり。`01` の軸 B。 |
| 技法 | テスト設計手法（境界値、状態遷移、ペアワイズ、探索的、…）。`01` の軸 C。 |
| 非機械的検証 | 人間の判断・探索・直感を要し、完全自動化できない検証。 |
| オラクル | 正否を判断する基準（設計書・旧実装・標準・経験）。 |
| SBTM | Session-Based Test Management。時間制の探索的テスト運用。 |
| チャーター | 探索的セッションの目的・対象・狙いを記した指示。 |
| DS | Data Set。検証前提データ。 |
